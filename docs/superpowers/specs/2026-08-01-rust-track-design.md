# Rust track for `xraph/workflows` — Phase 2

Date: 2026-08-01
Status: Approved design, not yet implemented
Extends `2026-07-31-generic-xraph-workflows-design.md`

## Context

Phase 0+1 renamed `xraph/go-workflows` to `xraph/workflows`, added a
language-agnostic `semantic-release.yml` spine, and migrated four Go
repositories. Phase 2 was planned as "the Rust track, harvested from `octopus`
and `farp/farp-rust`". Investigating those two repositories changed the scope.

## The finding that reshaped this phase

**A shared Rust *release* workflow would be built for no consumer.** The org has
exactly two Rust codebases, and neither can adopt one.

| repo | release model | why it cannot move |
|---|---|---|
| `octopus` | `release.yml` is **generated by cargo-dist 0.32.0** from `dist-workspace.toml` — four targets, shell and Homebrew installers, and custom `publish-jobs` for crates.io, Docker, Helm and Windows | The file is machine-generated and says so in its header. Replacing it means abandoning cargo-dist and losing installers, checksums and the artifact matrix; any hand edit is overwritten on regeneration |
| `farp/farp-rust` | A crate *inside* the `farp` Go repository. Released by farp's semantic-release plus `cargo publish`, with an assertion that `Cargo.toml`'s version matches the git tag | Its version *is* farp's version (`1.3.0` at both). It cannot be released independently |

This is the same pattern that kept `spindle` and `farp` out of Phase 1 — the
sophisticated repo is already ahead — but sharper, because cargo-dist's output
is generated rather than authored.

**What is genuinely harvestable is CI.** `octopus/.github/workflows/ci.yml` is
403 hand-written lines across nine jobs. Roughly half generalizes.

## Goal

Add `rust-ci.yml` to `xraph/workflows`, harvested from `octopus`. Wire `octopus`
up as the full consumer and `farp`'s `rust-test` job as a partial one.

Explicitly out of scope, and not deferred but *rejected*: a `rust-release.yml`.
cargo-dist owns `octopus`'s releases and semantic-release owns `farp-rust`'s.
Both work. Neither should be replaced.

**Honest accounting of the payoff.** This is one full consumer plus one partial,
against the Go track's four. It is worth doing because it establishes the Rust
track for future repositories and removes roughly 150 duplicated lines, but it
is a smaller win than Phase 1 and should not be sold as more.

## Architecture

Five jobs, preserving `octopus`'s fast/slow split. Only `lint`, `audit` and
`test` gate merges; the expensive legs run on `main` and a nightly cron so
per-PR feedback stays fast. That split is `octopus`'s existing design and is
carried over deliberately.

| job | gates merges | does |
|---|---|---|
| `lint` | yes | rustfmt and clippy |
| `audit` | yes | `cargo-audit`, installed prebuilt via `taiki-e/install-action` |
| `test` | yes | ubuntu + stable: build and test |
| `test-extended` | no | OS × toolchain matrix, off unless the caller asks |
| `docs` | no | `cargo doc`, uploads the artifact, off by default |

### Per-target Makefile detection transfers unchanged

`octopus` drives everything through `make fmt`, `make clippy`, `make audit`,
`make build`, `make test` and `make docs` — the same shape the Go repositories
use. `rust-ci.yml` therefore reuses `go-ci.yml`'s proven probe: test whether the
specific target resolves, and fall back per target otherwise.

| target | fallback |
|---|---|
| `fmt` | `cargo fmt --all -- --check` |
| `clippy` | `cargo clippy --all-targets --all-features -- -D warnings` |
| `audit` | `cargo audit` |
| `build` | `cargo build --all-features` |
| `test` | `cargo test --all-features` |
| `docs` | `cargo doc --no-deps --all-features` |

The clippy fallback denies warnings, which is stricter than `farp`'s current
`-W clippy::all`. That is intentional for a workflow whose job is raising the
floor; a repository that wants a laxer policy expresses it in its own Makefile,
which the probe then prefers.

Each job writes which path it took to `$GITHUB_STEP_SUMMARY`, as `go-ci.yml`
does, so the effective command is recoverable from the run page.

## Inputs

| input | type | default | notes |
|---|---|---|---|
| `working-directory` | string | `.` | `farp-rust` is a subdirectory |
| `toolchain` | string | `stable` | |
| `run-extended` | boolean | `false` | caller passes its own policy expression |
| `extended-matrix` | string | `'[{"os":"macos-latest","toolchain":"stable"},{"os":"ubuntu-latest","toolchain":"nightly"}]'` | JSON array; `octopus`'s existing matrix |
| `build-docs` | boolean | `false` | |
| `skip-audit` | boolean | `false` | |
| `system-deps-ubuntu` | string | `''` | apt packages |
| `system-deps-macos` | string | `''` | brew packages |

### Why `run-extended` is a boolean rather than a schedule

A reusable workflow cannot declare `schedule`, and the decision of *when* the
expensive matrix runs is a per-repository policy. The caller passes
`run-extended: ${{ github.event_name == 'schedule' || github.ref == 'refs/heads/main' }}`,
keeping the policy where the triggers already live.

### Why system dependencies must be inputs

Every `octopus` job installs `pkg-config libssl-dev protobuf-compiler`, and its
macOS leg runs `brew install protobuf`. Rust crates routinely need native
toolchains that Go's static builds never do. Hardcoding a list would be wrong
for other consumers; omitting the capability entirely would make the workflow
unusable by `octopus`, its only full consumer.

## Permissions

Every job declares `permissions: contents: read` as its ceiling. Unlike
`go-ci.yml`, nothing here uploads SARIF, so no job needs `security-events:
write` — `cargo-audit` reports through the job log and exit status.

Consequently callers of `rust-ci.yml` need only the default read token and do
**not** need a `permissions:` block, unlike `go-ci.yml`'s callers. The
difference is worth stating explicitly in the README, because the two Go and
Rust CI callers otherwise look interchangeable and are not.

## Pinned versions

Resolved 2026-08-01:

| action / tool | pin |
|---|---|
| `actions/checkout` | `v7` |
| `actions/upload-artifact` | `v7` |
| `Swatinem/rust-cache` | `v2` |
| `taiki-e/install-action` | `v2` |
| `dtolnay/rust-toolchain` | `@stable`, or `@master` with an explicit `toolchain:` for non-stable |

`Swatinem/rust-cache` replaces manual `actions/cache` steps entirely — it caches
the registry index, downloaded crates, git dependencies and the target
directory. No separate cache step is added, matching the `setup-go` decision in
the Go track.

`dtolnay/rust-toolchain` is tag-based rather than released: `@stable` is a
moving branch. That is the ecosystem's normal usage and is what `octopus` and
`farp` already do.

## What stays local to `octopus`

`coverage`, `bench`, `build-release` (four targets), `docker`, the vendored Helm
CRD staleness check, the examples build, and the `ci-success` required-check
gate. These are genuinely repository-specific; a shared workflow that absorbed
them would be `octopus`'s CI with extra indirection.

**This migration is not a drop-in.** `octopus`'s current `test` job mixes shared
concerns (build, test) with local ones (the CRD check, building examples).
Adopting `rust-ci.yml` means splitting those local steps into their own job. The
implementation plan must treat that as a real edit to `octopus`'s CI, not a
mechanical substitution.

## What changes in `farp`

`farp`'s `rust-test` job becomes a caller with `working-directory: farp-rust`.
It currently guards every step on `[ -f farp-rust/Cargo.toml ]`, which was
defensive; the crate exists, so the caller is unconditional. Nothing else in
`farp` changes — its Go CI, its semantic-release pipeline and its Rust
publishing are untouched.

## Testing

1. **`actionlint`** with `shellcheck`, as for every workflow in the repository.
2. **A new fixture, `testdata/fixture-rust/`** — a minimal crate with **no
   Makefile**, so the smoke job exercises the cargo fallback path rather than
   the make path.
3. **A smoke job** in `self-test.yml` calling `rust-ci.yml` against that
   fixture, with `skip-audit: false` so the audit path is genuinely run.
4. **Real proof:** `octopus`'s CI green on the shared workflow.

Phase 1 ended with two defects that produced valid but empty output while every
check passed. The lesson carried here: assert on observable behavior, not on
exit codes. Each job records its resolved command source in the step summary,
and the smoke job's value is confirming those resolutions are the expected
fallbacks — not merely that the run was green.

## Rules carried forward

Unchanged from the previous phases, and each already the cause of a real defect:

- No `${{ }}` expression inside any `run:` block; values pass through the step's
  `env:` as quoted bash variables.
- A step's own `env:` is not in scope in that step's `if:`.
- A `workflow_call` callee's `permissions:` can only narrow the caller's token,
  and GitHub validates every nested job's permissions at parse time, including
  `if:`-skipped jobs.
- Conventional commits, and no `Co-Authored-By` trailers.
